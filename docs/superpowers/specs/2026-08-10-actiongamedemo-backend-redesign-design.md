# ActionGameDemo 后端化重新定义设计

## 背景

原项目定位为 Unity 第三人称动作游戏 Demo + Java 权威服务端，美术表现占比较高。目标岗位是游戏后端/服务端开发，因此需要把项目主体从客户端表现切换到服务端能力，Unity 只保留验证客户端角色。

## 新定位

Realtime Combat Server：一个以实时对战服务端为核心产品的完整后端项目。它负责协议设计、房间管理、50fps 帧同步、权威战斗、反作弊、回放、压测与可观测性；Unity 客户端只是验证用的 Demo，不是项目主体。

## 核心原则

- 服务端权威：所有战斗判定在 Java/Netty 服务端执行，客户端禁止修改权威数值。
- Unity 降级：不新增建模、美术、VFX 工作，客户端只保留输入采集、协议联调和表现验证。
- JD 对齐：每个模块都能对应大厂游戏后端秋招 JD 的一个高频能力点。

## 模块边界

1. 网络层 `net`：WebSocket 二进制协议、Netty Pipeline、编解码、会话管理、消息分发。
2. 房间层 `room`：房间生命周期、帧调度、快照广播、断线重连、资源回收。
3. 战斗层 `battle`：伤害流水线、Buff 引擎、AI FSM、Boss 阶段、技能系统。
4. 安全层 `anticheat`：三层检测、响应策略、审计日志。
5. 回放层 `replay`：战斗录制、存储、回放执行。
6. 数据层（补齐）：MySQL 对局与玩家持久化，Redis 房间与匹配缓存。
7. 可观测层（补齐）：指标、日志、告警、Dashboard。
8. 工具链：压测工具、benchmark 报告、Docker 一键部署、CI/CD。
9. LLM 扩展：战斗复盘、难度调整、异常行为研判。

## 数据流

客户端连接后依次完成登录、加入房间、发送玩家操作；服务端以固定步长推进帧，执行战斗、AI 与 Buff 结算，并以快照广播回客户端。战斗过程同时写入回放与审计；LLM 分析在局后离线执行。

## 面试可讲的故事

- 帧同步与一致性：固定步长 20ms，客户端预测与回滚，0.5m 偏差阈值。
- 权威战斗：5 步伤害流水线，Buff 叠加规则与状态机。
- 反作弊：三层检测、分级响应、审计留痕。
- 稳定性：断线重连、对象池、资源回收。
- 工程化：单元测试、协议测试、Docker 部署。
